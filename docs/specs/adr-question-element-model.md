# ADR：以“元素（Element）”作为题目内容的基本单位

- 状态：提议（Proposed）
- 范围：全学科题库的内容模型；本文是**目标态**与**过渡策略**，不包含本次实现

## 背景

### 动机

题库的下一阶段目标是**结构化入库**：把题干拆成条件元素，把解答拆成步骤，并沉淀受控词表，使检索、命题分析和基于元素组合的原创命题成为可能。结构化需要覆盖所有学科，因此内容模型必须学科无关，学科差异只能落在配置与数据上。

### 现状

题目由整块富文本组成：`content`、`options`、`answer`、`thinking`、`analysis`、`summary`。结构化信息仅有粗粒度的标签和知识点。

材料题由独立实体 [`Stimulus`](../../backend/app/models/stimulus.py) 表达：

- `stimuli` 表，字段包括 `content`、`status`、`visibility`、`revision`、`content_revision`、`deleted_at`、`metadata`。
- `questions.stimulus_id`（单个外键）与 `stimulus_position`（带唯一约束）。
- 约 500 处代码引用，涉及组卷快照、docx/latex 导出、去重、导入、媒体引用、MCP 工具。

### 问题：`Stimulus` 在第一性原理上是过度特化的设计

1. **把“角色”建成了“实体类型”。** “材料”描述的是内容在题目中起什么作用（提供上下文、不可作答），而不是它是什么。这个角色被固化成一张独立的表。
2. **基数写死。** 单个外键只能表达“一道题对应一份材料，材料下挂多道小题”。真实场景中常见：
   - 材料一、材料二（历史、政治、语文）：一道题引用多份材料。
   - 选词填空、配伍选择的共享词库：被多题共享，但不是“材料”。
   - 理化共享的实验装置或图；只被其中几个小问共享的图表。
3. **生命周期重复。** `Stimulus` 重新实现了 `Question` 已有的状态、可见性、乐观锁、内容版本、软删除，以及去重、媒体引用、导入、导出等周边逻辑。二者属性相同，说明它们是同一类东西（内容单元）的不同角色。
4. **阻碍结构化。** 材料需要拆出出处、体裁、数据表等信息，现有的 `metadata_json` 只是临时容器，且与题目侧的结构化方案重叠。

## 决策

### 1. 元素是内容的基本单位

引入 **Element**：一个有角色的内容单元。

| 字段 | 含义 |
| --- | --- |
| `role` | 角色，如材料、对象、约束、已知、未知、设问、选项库、图。角色集合由学科 profile 配置 |
| `kind_id` | 元素类型（受控），决定 `params` 的 JSON Schema |
| `term_id` | 受控词表项（可空） |
| `raw` | **权威内容**（RichDoc），任何情况下都足以渲染 |
| `params` | 结构化参数（JSON，可空），按 `kind` 的 Schema 校验 |
| `subject_id`、`status`、`visibility`、`revision`、`content_revision`、`deleted_at` | 内容单元的统一生命周期 |

关键约束：**`raw` 是权威，`params` 是可选的渐进增强。** 只有 `raw` 的元素就是“未结构化”的内容，题目照常渲染、导出。结构化程度是元素自身的属性，而不是外挂的一层，因此不存在“旁路数据与权威数据冲突”的问题，也不需要区分“已结构化的题”与“未结构化的题”两套模型。

### 2. 题目通过多对多链接引用元素

```
elements(id, subject_id, role, kind_id, term_id, raw, params, status, visibility, revision, content_revision, deleted_at, ...)
question_element_links(question_id, element_id, position, rel)
```

- **共享**就是“一个元素被多个题目链接”，不需要特殊机制。材料一、材料二、共享词库、共享图都自然成立。
- 一道题对同一元素可有不同的 `rel`（如“上下文”“被引用”），`position` 控制渲染顺序。
- 题目保留**可作答单元**的职责：题型、答案、难度、审核、可见性仍属于 `questions`。

### 3. 层级是正交问题

“大题 → 小题”的父子关系与“内容共享”是两件事，不能混在一个机制里。层级用题目自身的父子关系表达（本 ADR 不展开，另行决策）。

### 4. 解答与步骤

解答步骤是另一类内容单元，属于“解答结构化”范畴，沿用同样的原则：`raw` 权威，`params` 渐进。步骤依赖用 DAG 表达。详细设计见后续的 `question-structure` 规格。

### 5. 学科差异只落在配置与数据

框架（元素、步骤、词表、关系、版本、审核）与学科无关；各学科通过 profile 提供角色集、元素类型及其 `params` Schema、词表和抽取 prompt。**新增学科 = 新增配置，而不是改代码。**

## 过渡策略

存量用户和数据很多，`Stimulus` 的依赖面大，**不做一次性替换**。分三步：

### 阶段 A：冻结（立即生效）

- 不再向 `stimuli` / `questions.stimulus_id` 增加新功能。
- 凡是“一题多材料”“共享词库”“共享图”等 `Stimulus` 无法表达的需求，**走元素模型实现**，不得把 `stimulus_id` 扩成多对多。

### 阶段 B：适配

- 新结构层按共享元素设计。
- 增加适配：每个 `Stimulus` 映射为一个 `role=material` 的元素，通过 `source_stimulus_id` 关联；适配层只读，`Stimulus` 仍是写入的权威。
- 材料内部的进一步拆解（出处、体裁、数据表）在映射出的元素下进行，不再写入 `metadata_json`。

### 阶段 C：收敛

满足以下**全部**条件后，才启动收敛迁移：

1. 元素模型已在至少两个**差异大**的学科（如数学与语文）验证通用，无需改动引擎。
2. 组卷、导出、导入、去重、媒体引用、MCP 均已有基于元素的实现并稳定运行。
3. 新增的“一题多材料”类需求已全部走元素路径，没有回退到 `stimuli`。

收敛方式是把 `stimuli` 数据迁移为元素与链接，保留 `stimulus_id` 一个版本周期作只读兼容，随后移除。迁移必须使用 `data_migrations` 框架，可分批、可回滚、可重复执行，并通过 `content_revision` 保证组卷快照不被误判为过期。

## 后果

### 好处

- 模型统一：共享内容、材料、条件元素、选项库用同一机制表达。
- 生命周期（状态、版本、软删除、去重、媒体引用）只实现一次。
- 结构化渐进：不需要“全库一次结构化”，也不需要两套渲染路径。
- 新学科只需配置。

### 代价与风险

- **两套模型并存期**（阶段 A–C）有认知和维护成本。缓解：阶段 A 的冻结规则要明确写入贡献指南，适配层保持只读。
- **题干粒度**：元素拆得过细会增加写入和渲染复杂度，过粗则无法组合。缓解：先在 20 道真题上试拆，再固定角色集。
- **性能**：题目渲染需要多一次关联查询。缓解：按题目批量预取元素并缓存，渲染结果沿用现有 RichDoc 管线。
- **词表治理依赖学科负责人**，技术方案不能替代内容运营。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 保持现状，仅在 `Stimulus.metadata_json` 中放结构化数据 | 否决：学科差异无法约束，且与题目侧结构化分裂 |
| 把 `stimulus_id` 扩成多对多（`question_stimuli`） | 否决：只解决基数，仍保留重复的生命周期与“角色即实体”的问题 |
| 采用“大题 → 小题”父子树，材料作为父节点内容 | 暂不采纳：解决层级，但无法表达跨题共享与非材料类共享内容（共享词库、共享图）。层级可在另一个决策中独立引入 |
| 一次性把 `stimuli` 迁移为元素 | 否决：改动面过大，存量用户风险高，且元素模型尚未经多学科验证 |

## 待决问题

1. 元素的审核状态是否独立于题目？（倾向：元素有自己的 `status`，题目发布时要求其链接的元素均为可见状态。）
2. 元素是否允许跨学科共享？（倾向：否，沿用“比对范围限同学科”的原则。）
3. 词表是全局共享、按学科共享，还是按用户/机构隔离？取决于多租户的产品决策。
4. `kind` 的 `params` Schema 的编辑权限：仅管理员，还是学科负责人。
5. 题目层级（大题 → 小题）的建模，另起 ADR。
